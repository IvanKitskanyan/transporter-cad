# Transporter CAD: сборка конвейеров, спецификации, библиотека

Все операции — через AutoCAD COM (PowerShell) + LibreDWG (`dwg elements/convert/dwg2dxf.exe`, `dwggrep.exe`).
Скрипты этого скилла самодостаточны; путь к библиотеке: `.claude/skills/transporter-cad/lib/elements.json`.

## Главные правила (вшитые уроки)

1. **Самокоррекция вставок.** Любой элемент вставляется → замеряется `GetBoundingBox` → `Move` к расчётной точке → повторный замер (допуск 0.01 мм). Это автоматически компенсирует INSBASE, базовые точки и staging-смещения ЛЮБОГО нового элемента. Никогда не доверяй первому размещению.
2. **Вставка только DWG.** `InsertBlock` принимает только `.dwg`. Исходник в DXF → сначала сохраняй/получай DWG-версию (у пользователя модели всегда есть в `dxf elements/` и `dwg elements/`).
3. **DXF-выход — только LibreDWG.** COM `SaveAs` в DXF ненадёжен (пишет `.dxf.dwg`: сохраняет DWG). Рецепт: `doc.SaveAs(out.dwg)` → close → `dwg2dxf.exe -v0 --as r2004 out.dwg` в каталоге `dwg elements/convert/`, затем переместить результат.
4. **COM-гигиена.** Медленный старт AutoCAD (~1 мин): цикл ожидания `GetActiveObject` (до 5 мин, при пустом старте `Start-Process acad.exe`). Все вызовы — через `Retry` (RPC_E_CALL_REJECTED, таймаут ≥300 попыток). Большие DXF (>20 МБ) в COM НЕ открывать — только DWG. Зависший AutoCAD → `taskkill //IM acad.exe //F`, подождать регистрации в ROT.
   **Локи (.dwl/.dwl2):** если DWG открыт у пользователя в AutoCAD, `SaveAs` в тот же путь из другого документа МОЛЧА проваливается (файл на диске не меняется, ошибка может не всплыть; реальный случай: правка трансфера 19.10 была «сохранена», но файл остался старым — пользователь увидел баг). Перед сборкой проверять: `[IO.File]::Open(path,'Open','ReadWrite','None')` — Locked → либо править на месте через `GetActiveObject` (найти doc по FullName → Move → `doc.Save()`), либо сохранять результат под новым именем и явно сказать пользователю.
5. **Датумы склейки** (см. `lib/elements.json`): секция — низ датчиков (8652.129) на плоскость этажа; горка — **ВЕРШИНА (union top 2956.847) на плоскость стола трансфера (верх ленты верхнего этажа − 8.643)**, выход — низ U647 (−385.328) на плоскость нижнего этажа; Z-масштаб `fz = (gap + 95.857)/3342.175`; трансфер — верх площадок (8760.272) на уровень ленты (плоскость + 104.5). Урок 20.10: старый датум «низ U646 → плоскость верхнего этажа» давал вершину горки на +153 мм ВЫШЕ стола трансфера — в эталонном «Общем чертеже» вершина горки = плоскость стола U86 (ins z), площадки U746 на 8.643 выше.
6. **Комповка «серпантин»** (подтверждено пользователем): этажи друг над другом, одна ось X 0..50000; горки на ПРОТИПОЛОЖНЫХ концах (восток → запад → восток...). ВАЖНО: rot=180 горки/трансфера зеркалит и Y-смещение устройства: восточный спуск (rot=0) уводит нижнюю линию на Y **−1083,761**, западный (rot=180) возвращает на +1083,761. Линии попарно чередуются по Y (0, −1083,761, 0, −1083,761...) — «секции на этажах идут под друг другом» с учётом осевых смещений. Величина 1083,761 = точная разность центров полос секции/горки в собственной раме трансфера (`transfer.gorka_line_dy`); ранее ошибочно стояло 1091 и гасилось костылём 7,239 мм — костыль УБРАН, при неверном dy горка расходится с линией-приёмником по Y.
7. **Оверлапы ~36–53 мм** на стыках (адаптер ↔ U646, адаптер ↔ конец ленты) — норма, так в исходной сцене пользователя. Не «чинить».
8. **Формулы серпантина** (X_e = восточный конец верхней линии; X_w = западный; верхняя линия Y=y_u; плоскость нижнего этажа Z_l; beltTop = Z_u + 104.5):
   - Восток (rot=0): gorka ins.x = X_e − 204259.154; transfer ins.x = X_e − 53.232 − 121236.438; оба ins.y = y_u − 80542.275.
   - Запад (rot=180): gorka ins.x = X_w + 204259.154; transfer ins.x = X_w + 53.232 + 121885.838; оба ins.y = y_u + 80542.275.
   - Линия-приёмник начинается у ВЫХОДНОГО торца горки: восточный спуск → её восточный конец = X_e − 10689,6; западный → западный конец = X_w + 10689,6.
   - **Авто-анкоринг приёмника**: `build_conveyor.ps1` сам переставляет `x_start`/`y` линии-приёмника каждого спуска (с предупреждением ANCHOR в отчёте), чтобы её торец вошёл в выходную грань горки, а ось — на ось спуска. `x_start`/`y` такой линии в конфиге задавать необязательно — скрипт исправит. Цепочка серпантина обрабатывается в порядке drops (верхние этажи первыми!).
   - Полная реализация: `scripts/build_conveyor.ps1` — формулы уже в коде. В отчёте смотреть строки **JOIN**: `dx`/`dy` стыка горка↔линия и `adapter_join_dx` трансфера должны быть ~0; `far_overhang` трансфера ≈ 851,8 мм за конец линии (восток) — НОРМА, стол разворота торчит за торец линии (так в эталоне), не путать с отрывом.
9. **PowerShell-грабли** (проверено на практике):
   - `.ps1` с кириллицей — ТОЛЬКО UTF-8 **с BOM** (Write tool пишет без BOM → при первом запуске добавить BOM);
   - кириллические ключи в хэш-литералах `@{ № = ... }` — невалидны (использовать латиницу);
   - `InsertBlock` НЕ принимает пути с `/` — только `\`;
   - переменные PS регистронезависимы: не называть Streamwriter-локалы `$csv`/`$md` при наличии путей `$CSV`/`$MD`;
   - чтение JSON: `Get-Content -Raw | ConvertFrom-Json` в ряде инвокаций возвращал строку-ToString объекта вместо объекта; рабочий рецепт — `[IO.File]::ReadAllText` + ретрай парса, а построение справочников — в ИЗОЛИРОВАННОЙ функции (своё scope);
   - консоль PS выводит кириллицу в CP866 — в пайпе bash это выглядит как мусор: для проверок писать в файл (UTF-8+BOM) и читать Read-инструментом.
10. **Рендер сверки** — `scripts/render3d.ps1 -Dxf x.dxf -Proj XY|XZ|YZ`. Рендер — только по запросу пользователя (файлы большие, парс медленный). Сверка позиций — по COM-замерам bbox.

## Задача 1: Собрать конвейер на N этажей

1. Составь JSON-конфиг (схема и пример: `configs/serpentine4.json`). Минимум для линии:
   `{"z": плоскость_этажа|3000, "y": ось_линии, "x_start": 0, "count": 4, "pitch": 12500, "element": "section"}` — либо `"length": 50000` вместо pitch (посекционно равномерная растяжка, scale_x = pitch/11699.991).
2. Спуски: `{"upper": индекс_линии, "side": "east|west", "y_side": -1|1, "gorka": "gorka", "transfer": "transfer"}`.
3. Зона сортировки / любые сторонние модели: блок `extra` в конфиге: `{"element": "имя_в_библиотеке", "ins": [x,y,z], "rot": градусы, "expected_min": [x,y,z]|null}`.
4. Запусти: `powershell -File scripts/build_conveyor.ps1 -Config <путь.json>` (фон! вставки тяжёлые — каждый ~60–90 с). Скрипт пишет отчёт `<out>_report.txt` и проводит VERIFY-замер всех вставок.
5. DXF: `dwg2dxf.exe -v0 --as r2004 <out.dwg>` → переместить в корень проекта.
6. Сверка: отчёт (UNION bbox, все CHECK). Погрешности сборки > 0.5 мм — расследовать.

## Задача 2: Спецификация (BOM)

`powershell -File scripts/make_spec.ps1 -Dwg <итоговое.dwg> -Lib lib/elements.json -Out <имя_спеца>`
Выдаёт CSV (UTF-8 BOM, открывается в Excel) + Markdown-сводку: по типам элементов — количество, суммарные длины; по линиям (группировка по Z-планам) — длина, число секций; позиции всех вставок. Прогонять и ПОСЛЕ сборки, и по любому чужому DWG.

## Задача 3: Расширение библиотеки элементов

1. Пользователь кладёт модель в `dwg elements/` (DWG) и/или `dxf elements/` (DXF).
2. `powershell -File scripts/probe_element.ps1 -Dwg <модель.dwg> -Name <ключ_элемента>` — замерит modelspace (все вставки + union-bbox), добавит/обновит запись в `lib/elements.json`.
3. Заполни руками в JSON датумы нового элемента (`datum_z`, точки стыковки) — расспроси пользователя о плоскостях склейки, они должны быть согласованы с остальными элементами. Проверь результат: вставь пробный экземпляр и сверь bbox.
4. Элемент может быть НЕ конвейерным (датчики, рамы, зоны) — тогда в entry достаточно `raw` + `label`; размещение — через `extra` в конфиге сборки.
5. Если модель обновилась — повтори probe (entry обновится, конфиг пересобирается заново).
